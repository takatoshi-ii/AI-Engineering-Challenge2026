# 社外コンペでRAGを作った話 ― ローカルLLMだけで社内ドライブ100問に答える

SIGNATE「AI Engineering Challenge ～煩雑な社内ドライブをハックせよ～」に参加しました。
結果は Private 0.5071（上位は0.92〜0.98）で勝てませんでしたが、業務に流用できそうな知見がかなり溜まったので共有します。特に **LLMを業務に組み込むときに踏みやすい罠** と、**ローカルLLMを実運用規模で回したときの実測値** は、そのまま使えると思います。

---

## 1. どんな課題だったか

未加工の社内共有ドライブ（403ファイル／10案件／14形式）と質問文だけを入力に、100問へ自動回答するRAGを作る、というものです。

ドライブの中身は、契約書・提案書・報告書・会議録・Excelのデータ・Jupyter Notebook・座席表の画像など、実際の業務フォルダそのものでした。

### 規約が厳しい

以下が全部禁止でした。

- 人手で作った一覧表やDBの読み込み
- 設問ごとの参照ファイルや正解候補を事前に用意すること
- 質問文を見た固定回答や、案件名を狙い撃ちした専用分岐
- 答えの金額・担当者名・ページ番号・セル番地をコードやプロンプトに書くこと

要するに **「設問を知らないシステム」を作れ** という課題です。

案件の略称も、保護ファイルのパスワード導出規則も、決裁基準も、すべて実行時にドライブ内の文書を読んで解決させる必要がありました。未知の案件フォルダが増えても同じ処理で動くことが、規約適合の証明になります。

### 設問の性質

質問文を機械的に分類すると、こうなりました。

| 要求されること | 問数 |
|---|---:|
| 計算・集計（合計・差・平均・閾値など） | 24 |
| 書式・色（太字・黄色ハイライト・赤字） | 18 |
| 版の比較（old版との差分） | 9 |
| 全案件横断の集計 | 9 |
| 図・画像（ヒストグラム・座席表） | 5 |
| ページ位置（何ページ目か） | 4 |
| 上記いずれも明示されていない | 39 |

**6割が何らかの道具を要求します。** 検索して上位k件を渡すだけの古典的なRAGでは届きません。

---

## 2. 作ったもの

```
共有ドライブ → 形式別の抽出 → BM25索引 → エージェント（道具9種）→ 回答
```

Python 約7,100行。質問文による分岐はコード中に一箇所もなく、100問すべてが同一のエージェントループを通ります。

エージェントが持つ道具は以下の9つです。

| 道具 | 役割 |
|---|---|
| `list_files` | 案件やパターンでファイルを絞り込む |
| `search_corpus` | 抽出済み全文へのキーワード検索 |
| `read_document` | 本文を読む（offsetで続き、grepで範囲指定） |
| `locate_in_pages` | 語がどのページにあるか引く |
| `lookup_glossary` | 略称と案件名の対応を用語集から引く |
| `run_python` | サンドボックスで実際に計算する |
| `list_images` | ファイルや案件に紐づく画像を列挙 |
| `view_image` | 図・座席表・画像PDFを実際に見る |
| `submit_answer` | 回答・根拠・確信度を提出 |

1問あたりの道具呼び出しは中央値8回、最大84回。100問で計1,171回でした。

## 3. なぜローカルLLMで完結させたか

個人所有のDGX Spark上で、**回答生成を完全にローカルで実行**しました。上位勢の多くは OpenAI / Claude のAPIを使っています。

あえて使わなかった理由は、**課題の前提がそれを要求しているから**です。

対象は「社内の共有ドライブ」、つまり契約書や顧客データが入ったフォルダです。実務でこの種のデータを扱うとき、外部APIへ送信できない組織は珍しくありません。データ持ち出しの制約があるからこそ、社内にドライブが積み上がっているわけです。

外部APIを使った時点で、そのシステムは「データを外に出せる組織」でしか使えません。**ローカルで完結することは、このユースケースにおいて機能要件そのもの** だと判断しました。

副次的に、再現性（固定ハードで12時間の制約内に収まることを自分で保証できる）と、コスト（API課金が試行回数に比例しない）という利点もありました。

OpenAIのAPIキーは取得しましたが、用途を公式採点器による検証のみに限定し、回答生成には一度も使っていません。

### その代価

正直に書くと、**この方針は精度を犠牲にしました。** 上位0.92〜0.98に対して0.5071です。

ただ、制約を課したこと自体は判断であり、その代価がいくらだったかを測れたことには意味があると考えています。後述しますが、失点14問のうちモデルの能力に起因するものと、実装で防げたものは分けられています。

## 4. 一番効いた設計：書式をテキストに埋め込む

「太字の箇所は」「黄色ハイライトのセルの抽出条件は」という設問が18問ありました。本文テキストだけ抜いても、これらは原理的に解けません。

そこで抽出時に、書式をマーカーとして本文へ埋め込みました。

```
[[bold]]…[[/]]        太字
[[hl:yellow]]…[[/]]   黄色ハイライト
[[color:red]]…[[/]]   赤字
塗り=red(...)          図形の塗り色
```

これで **「書式に関する問い」が「普通のテキスト検索の問い」に変わります。** エージェントに専用の道具を増やさずに済むのが利点です。

社内の文書検索システムでもそのまま使える発想だと思います。「赤字で書かれた注意書きを探す」といった要求に、検索エンジンを変えずに対応できます。

## 5. 形式別のハマりどころ

遭遇しないと気づけない類のものを並べます。

### 色は「番号＋補正値」で入っていることがある

OOXMLはセルや文字の色を「テーマ色の番号＋明度補正(tint)」で保持する場合があります。番号のままでは黄色かどうか判定できません。`theme1.xml` を読んで実RGBに解決する処理が必要でした。

少数派の色をハイライトとみなすヒューリスティクスと組み合わせて、ようやく「黄色ハイライト」が扱えるようになります。

### ページ番号はXMLに存在しない

docx や pptx に「何ページ目か」という情報はありません。**レンダリング結果として初めて決まる** ためです。

MS Office の COM オートメーションで実際に開かせ、レイアウト実測のページ割りを取得して抽出テキストに書き込みました。地味ですが、これなしでは「見出しは何ページ目か」系の設問が全滅します。

### ヒストグラムは通常のグラフXMLにいない

Excel 2016以降のヒストグラムは `chartEx` パートに、ビン分割の定義とともに格納されます。ここを読まないとビン幅も度数も取れません。

### 斜体がフォント属性ではないPDFがあった

あるPDFのイタリックは、フォントのフラグではなく **テキスト行列 `Tm` の傾き成分（c≈0.3333）** で擬似的に作られていました。コンテンツストリームを解析して行列の歪みから判定しています。

### Notebookの埋め込み画像が索引を汚染する

`.ipynb` にbase64で埋め込まれた画像が、単一で510万文字ありました。これが索引全体を汚染していたため、画像を別台帳へ切り出す処理を追加しました。

## 6. 検索：BM25 ＋ 文字バイグラム

日本語の索引付けに形態素解析器を使いませんでした。意図的な判断です。

- 辞書が不要で、決定的に動作する
- `employment_length` や `Attr14` のような識別子を分割せず、そのまま一致させられる
- 形態素解析器は未知語の切り方が辞書に依存し、この種の語彙を壊しやすい

```
チャンク 5,877件 ／ 語彙 72,998種 ／ k1=1.4, b=0.72
```

埋め込みベクトルによる意味検索も未使用です。設問が「この案件のこのファイルのこの列」という指示的なものばかりで、語の一致で足りました。**外部の埋め込みモデルに依存しない構成にできた**のも、ローカル完結の方針と相性が良かった点です。

OCR結果（253枚）も索引に載せ、キーワード検索から画像内の記述に到達できるようにしています。当初これをやっておらず、画像内の情報は直接見に行かない限り到達できない状態でした。

## 7. DGX Spark の実測と罠

個人で購入した機材です。オンプレでLLMを動かす構成を検討する際の実測値として参考になると思います。

### 機材の性質

容量は128GBと潤沢ですが、**メモリ帯域が約273GB/sしかありません。** コンシューマGPU（RTX 3090で約936GB/s）に大きく劣ります。

LLMの生成は1トークンごとに全重みを読み出すため、帯域がそのまま速度を決めます。

```
273 GB/s ÷ 18 GB（モデルサイズ）≒ 15 トークン/秒
```

**容量は潤沢だが帯域が細い** という非対称な機材で、この前提で全ての設計判断をしました。

### モデル選定

4種を実機で比較しました。

| モデル | サイズ | 結果 |
|---|---:|---|
| `gpt-oss:120b` | 65.4GB | 不採用。ツール呼び出しのJSONが高頻度で破損 |
| `qwen3.8:27b-q8_0` | 30.0GB | 公式採点での比較を行えず、積み残し |
| `qwen3.5:35b` | 23.9GB | 検証役として使用 |
| `qwen3.8:27b` | 17.7GB | **採用**（Q4_K_M・文脈64k） |

本命は120B級のMoEでした。活性パラメータが小さいため、帯域が細いこの機材では密な27Bより速く動くはずだったからです。

しかし実行すると、ツール呼び出しの引数JSONが壊れていました。

```
{"ext":"docx","project":"SOHK","query":"工数",top_k":20}     引用符の欠落
{"limit":200,"offset":500","plain":JSON?                      裸の値・途中で切断
{"code":"old = '''"+ (await None) + "'''"}                    JSON文字列内でPython連結
{"grep":"yellow", ... "株式会社青潮モビビ..."}                 文字の重複
```

本番投入前に検出できたのは収穫でしたが、スキーマ制約付きデコードや修復リトライで押し切る時間がなく断念しました。**モデル起因か基盤（Ollama）起因かの切り分けは未了** で、これは宿題として残しています。

### 踏んだ罠と対処

**文脈32kでは足りなかった**
差分比較の設問11問が一斉に文脈溢れで壊れました。64kに上げたうえで、予算ベースの刈り込みを実装しています。

```
予算 60,000文字を超えたら刈り込む
直近4件の道具結果は原文のまま、それ以前は要約に切り詰める
単一の結果は14,000文字で頭打ち
```

さらに、差分比較は全文を読ませず `run_python` の `difflib` に寄せるようプロンプトで誘導しました。**帯域が細い機材では、読ませる量を減らすこと自体が速度になります。**

**タイムアウトは「1問」ではなく「1呼び出し」の上限**
全案件横断の集計設問3問が、毎回 `model server unresponsive` で死んでいました。モデルの無応答を疑いましたが、原因はクライアント側のタイムアウトでした。

これらは文脈が突出して大きくなる設問で、**1回のプリフィルが上限を超えていた** わけです。

```
420秒   3問とも失敗
900秒   1問回復（657秒・17呼び出し）
1800秒  もう1問回復
```

上限を上げるだけで2問が復活しました。一般的な設定値が通用しない場面があります。

**並列度を最後まで測っていなかった**

```
同一設問  1並列  27.0秒
         3並列  31.4秒   ← 遅延は16%増のみ
```

遅延が16%しか増えないということは、**総スループットが約2.6倍** です。帯域律速の機材では、複数リクエストが重みの読み出しを共有するためバッチ処理が効きます。

1並列で100問6時間という前提のまま最終日まで進めてしまいました。早く測っていれば1実行2.5時間となり、12時間の制約内に3回の実行が収まって、断念した多数決が実現できていました。**最初に10分かけて測るべき種類のこと** です。

**発熱**
全力稼働で90℃級に達します。無人で長時間回す場合は注意が必要です。

## 8. 採点設計への対応

| 判定 | 配点 |
|---|---|
| Perfect（完全正解） | +1 |
| Acceptable（軽微な誤りを含む有用な回答） | +0.5 |
| Missing（わからない） | 0 |
| Incorrect（誤答・無関係） | **−1** |

誤答は「取れたはずの+1」と「−1」で **実質2点の損失** です。確信が持てないなら答えない方が期待値が高い。一方で、少し探せば分かることを諦めても0点にしかならない。この2つの衝突が設計の難所でした。

対処として、道具の呼び出しが9回に満たないうちに「わかりません」を出そうとしたら、一度だけ差し戻して具体的な追加手段を提示する仕組みを入れました。

1. `read_document` の offset を進めて最後まで読む
2. grep に別の語（言い換え・英語表記・略称・列名）を指定する
3. 全案件横断の集計なら `run_python` で一括走査する
4. 図やスキャンPDFなら画像を見る

同時に、差し戻しの文面には **「推測を求めているのではない」と明記** しました。探索を促す圧力は、放置すると当てずっぽうを誘発します。問われている対象を取り違えたまま計算する誤りは、「確認できない」より低い評価になるためです。

## 9. 測って捨てた施策

同じ道を通る人の時間を節約できるので、効かなかったものも残します。

### 回答の検証パス

誤答をIncorrect(−1)からMissing(0)に変えれば1問あたり+1点です。そこで、回答後に **まっさらな状態の別エージェントが独立に資料を確認し、否定されたら棄権する** パスを実装しました。

| 構成 | 測定結果 | 判定 |
|---|---|---|
| 同一モデルで検証 | 検証30問で誤答1件を捕捉。しかし本番36問連続で否定ゼロ | 実質無効 |
| 別モデル（35B）で検証 | 唯一の否定が正答に対する誤否定（−0.0333） | 逆効果 |

理由は明確で、**検証役が回答役と同程度に弱い** のです。同一モデルは自分の答えを支持し、別モデルは自信を持って正答を否定しました。誤りを見抜くには、誤りを犯さない側の能力が要ります。

LLMにLLMを検証させる構成を検討している方は、**検証側に明確な能力差があるか** を先に確認した方がいいです。

### 1問あたりの時間上限

長引く設問を打ち切って効率化しようとしましたが、調べると **長時間かかった24問のうち18問は「働いていたから長かった」**。850秒・49回の呼び出しを経て正答に到達した設問もありました。撤回しています。

### 回答の簡潔化プロンプト

冗長さが減点要因という仮説を立てましたが、実測すると回答は既に平均17文字・中央値7文字で、150文字超は0件。伸びしろ自体が存在しませんでした。

### 多数決（self-consistency）

同じ設問を3回解いて一致を採る手法は有効と判断しましたが、1実行6時間×3＝18時間となり、再現12時間の制約に収まらず断念しました。並列度を先に測っていれば実現できていた、というのは前述の通りです。

## 10. 自己採点は信用できない

最初はモデル自身に採点させていて、**0.9000** という結果が出ていました。

主催者の採点器（判定モデルはgpt-5.2）で同じ回答を測り直すと **0.7333**。自分の冗長さを甘く採点していたわけです。

ここで評価基盤を作り直し、正解データ付きの検証セット30問＋公式採点器でのみ良し悪しを判定するようにしました。**これをやるまで、改善の採否を客観的に決められていませんでした。**

社内でLLMの改善施策を評価する場合も、同じモデルに採点させる構成は避けた方がいいです。

---

## 11. 最大の反省：少ない問数で方針を決めていた

2つの提出版のスコア差です。

```
Public (30問)   22.0点 vs 19.0点  → 0.1000 の差
Private(70問)   35.5点 vs 35.0点  → 0.0071 の差
```

Publicは30問しかないので、**3問ぶれれば0.1動きます。** この差を「プロンプト変更の効果」だと解釈して方針を決めていました。Privateの結果を見ると、効果ではなく単なる揺らぎでした。

手元には正解データ付きの検証セットと公式採点器があったのに、**測定の分解能を超えた意味を読み取っていた。** 技術的な工夫より先に、この規律が必要だったと思っています。

業務でも、少数のサンプルでA/Bを判断する場面は多いので、自戒を込めて共有します。

## 12. 失点の中身と、一番の持ち帰り

Privateのスコアから内訳を逆算すると、概ねこうなります。

```
Perfect   約50問
Incorrect 約14問   ← 1問あたり2点の損失
Missing   約6問
```

**誤答14問を潰すだけで0.907相当まで届く計算です。** 「答えられない」より「間違って答える」方が問題でした。

その14問の中身がこれです。

- ヒストグラムの度数、ビンの範囲
- 座席表の位置関係、内線番号
- 閾値を変えたときのF1最大値
- ピボットの抽出条件

**全部、決定的な計算で答えが一意に決まる設問です。**

生データからExcelの分割規則で再計算する、画像の座標関係を解析する、といった実装に向かうべきでした。これをモデルに「見せて読ませて」いたのが敗因です。

モデルを賢くするより確実で、しかも安い。そして **これはモデルの強さとは独立した改善** なので、ローカルLLMのままでも実行できました。

LLMを使う案件全般に言えることだと思います。

> **機械で解けることは機械で解く。LLMには、機械で解けないことだけをやらせる。**

ここが一番の持ち帰りです。
