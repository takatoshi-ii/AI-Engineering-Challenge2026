# 煩雑な社内ドライブをハックせよ — 取り組みの記録

SIGNATE「AI Engineering Challenge」提出システムの設計・実装・検証の記録。

未加工の社内共有ドライブ（403ファイル／10案件）と質問文のみを入力として、100問に自動回答する RAG システムを構築した。**回答生成を完全にローカルLLMで完結させる**方針を採り、DGX Spark 上で全工程を実行した。最終スコアは Public 0.7333 / Private 0.5071。

---

## 1. 課題の性質と制約

### 評価基準

| 判定 | 配点 |
|---|---|
| Perfect（完全正解） | +1 |
| Acceptable（軽微な誤りを含む有用な回答） | +0.5 |
| Missing（わからない） | 0 |
| Incorrect（誤答・無関係） | **−1** |

**誤答が負の点を持つ**ことが、設計全体を規定した。誤答は「取れたはずの +1」と「−1」で実質 2 点の損失になる。したがって確信が持てない場合は答えないほうが期待値が高い。一方で、少し探せば分かることを諦めても 0 点にしかならない。この二つの要求が衝突する点に、設計上の難しさがあった。

### 規約上の制約

コンペは以下を禁じていた。

- 人手で整理した独自DB・一覧表の読み込み
- 質問ごとの正解候補・参照ファイル・重要ページを事前にまとめたファイル
- 特定質問の答え・金額・担当者名・ページ番号・セル番地をコードやプロンプトに書くこと
- 質問文を見て固定回答を返す分岐
- 案件名・ファイル名を狙い撃ちした専用処理

この制約を素直に受け取ると、作れるものは一つに絞られる。**形式ごとの汎用的な読み取り器と、それを道具として使うエージェント**である。

案件の略称も、保護ファイルのパスワード導出規則も、決裁基準も、すべて実行時にドライブ内の該当文書を読んで解決させた。未知の案件フォルダが増えても同じ処理で動くことが、規約適合の証明そのものになる。

**結果として、質問文による分岐はコード中に一箇所も存在しない。100問すべてが同一のエージェントループを通る。**

## 2. 方針 — ローカルLLMで完結させる

上位入賞者の多くは OpenAI や Claude などのフロンティアモデルをAPI経由で利用している。本システムは**意図的にその道を採らず、回答生成をすべてローカルで行った**。

### なぜローカルに限定したか

**課題の前提がそれを要求している。** この課題は「社内の共有ドライブ」を対象としている。契約書、見積、議事録、顧客データが入ったドライブである。実務でこの種のデータを扱うとき、**外部APIへ送信できない組織は珍しくない**。データ持ち出しの制約があるからこそ、社内にドライブが積み上がっている。

外部APIを使った時点で、そのシステムは「データを外に出せる組織」でしか使えない。**ローカルで完結することは、このユースケースにおいて機能要件そのもの**だと判断した。

副次的な理由として、以下もある。

- **再現性** — 固定されたハードウェアで、12時間の再現制約内に収まることを自分で保証できる
- **コスト** — API課金が実行回数に比例しない。試行錯誤の回数を気にせず回せる
- **外部依存の排除** — レート制限、モデルの差し替え、サービス障害に左右されない

OpenAI のAPIキーは取得したが、**用途を公式採点器による検証のみに限定**し、回答生成には一度も使用していない。

### その選択の代価

正直に書く。**この方針は精度を犠牲にした。**

```
上位入賞者（フロンティアモデル）   Private 0.92 〜 0.98
本システム（ローカル27B）         Private 0.5071
```

失点14問の多くは、正しい案件の中で計算や読み取りを誤ったものだった。より強いモデルであれば防げたものが含まれる可能性は高い。

**制約を課したこと自体は判断であり、その代価がいくらだったかを測れたことには意味がある**と考えている。本記録では、ローカルで戦うために何を実装したかと、それでも届かなかった差の両方を残す。

## 3. 全体設計

```
[1] 共有ドライブ          403ファイル / 14形式
        ↓
[2] 形式別の抽出           書式・色・数式・グラフ数値・ページ割り・OCR
        ↓
[3] 索引と画像台帳         BM25 5,877チャンク / 画像639件
        ↓
[4] エージェント  ←──┐    9種の道具 / 最大26手
        ↓          │
     道具の呼び出し ──┘
        ↓
    回答
```

[2][3] は事前に一度だけ実行し、`--force` で全再生成できる。中間生成物はすべて実行時に作られるため、「人手で整理したデータ」には当たらない。

実装規模は Python 約 7,100 行。

## 4. 形式別抽出器 — 最も時間を投じた部分

### 着想: 書式そのものが答えになる

設問には「太字の箇所は」「黄色ハイライトのセルの抽出条件は」「見出しは何ページ目か」といった問いが多数含まれる。本文テキストだけを抜き出す一般的な抽出では、これらは原理的に解けない。

そこで**抽出テキストに書式をマーカーとして埋め込む**方式を採った。

```
[[bold]]…[[/]]        太字
[[hl:yellow]]…[[/]]   黄色ハイライト
[[color:red]]…[[/]]   赤字
塗り=red(...)          図形の塗り色
```

これにより、**書式に関する問いが通常のテキスト検索の問いに変わる**。エージェントは専用の道具を持たずに「太字の箇所」を探せる。

### 対応した形式

| 形式 | 件数 | 抽出内容 |
|---|---:|---|
| `.docx` | 46 | 書式ラン、表、見出し階層、レイアウト実測のページ割り |
| `.pptx` | 25 | スライド本文、図形の塗り色、グラフの系列と値、ノート |
| `.xlsx` | 20 | セル値と数式、塗り色の使用状況、オートフィルタ、ピボットキャッシュ、条件付き書式(dxf)、chartEx |
| `.pdf` | 28 | ページ単位テキスト、擬似イタリック検出、画像ページ切り出し |
| `.ipynb` | 11 | セル入出力、埋め込み画像の分離 |
| `.png` | 54 | 画像台帳へ登録、OCRで本文化 |
| `.csv` / `.tsv` | 31 | スキーマと統計、全件走査の対象 |
| `.py` / `.md` / `.json` 他 | 188 | プレーンテキスト全文 |

抽出結果は 7.01 MB（約 230 万文字）。

### 個別に解決した問題

**テーマ色と tint の解決**
OOXML はセルや文字の色を「テーマ色の番号＋明度補正(tint)」で保持することがある。番号のままでは黄色か判定できないため、`theme1.xml` を読んで実RGBに解決した。少数派の色をハイライトとみなすヒューリスティクスと組み合わせて初めて「黄色ハイライト」が扱える。

**ヒストグラムは chartEx パートにいる**
Excel 2016 以降のヒストグラムは通常のグラフXMLではなく `chartEx` に、ビン分割の定義とともに格納される。ここを読まないとビン幅も度数も取れない。

**ページ番号は XML に存在しない**
docx や pptx に「何ページ目か」という情報は無く、レンダリング結果として初めて決まる。MS Office の COM オートメーションで実際に開かせ、レイアウト実測のページ割りを取得して抽出テキストに書き込んだ。

**斜体が斜体でない**
あるPDFのイタリックはフォント属性ではなく、テキスト行列 `Tm` の傾き成分（c≈0.3333）で擬似的に作られていた。コンテンツストリームを解析し、行列の歪みから斜体を判定した。

**パスワードを規則から導出**
保護ファイルのパスワードは、ドライブ内の規則文書に書かれたテンプレートから実行時に導出した。パスワードそのものをコードに書けば規約違反になるため、規則を読んで組み立てる以外に道がない。

**ノートブックの巨大画像による索引汚染**
`.ipynb` に base64 埋め込みされた画像（単一で 510 万文字）が索引を汚染していた。画像を抽出して別の台帳に移す処理を追加した。

## 5. 検索

日本語の索引付けに **BM25 + 文字バイグラム**（＋ASCII語は分割せず1トークン）を採用した。

```
チャンク  5,877 件
語彙      72,998 種
k1 = 1.4   b = 0.72
```

形態素解析器を使わなかったのは意図的な判断である。

- 辞書が不要で、決定的に動作する
- `employment_length` や `Attr14` のような識別子めいた語を分割せず、そのまま一致させられる
- 形態素解析器は未知語の切り方が辞書に依存し、この種の語彙を壊しやすい

埋め込みベクトルによる意味検索は使っていない。設問の多くが「この案件のこのファイルのこの列」という指示的なもので、語の一致が効くためである。**外部の埋め込みモデルに依存しないことは、ローカル完結の方針とも整合する。**

OCR 結果（253枚）も索引に載せ、**キーワード検索から画像内の記述に到達できる**ようにした。当初これを行っておらず、画像内の情報は直接見に行かない限り到達できない状態だった。

## 6. エージェント

最大 26 手のループを回り、道具を呼びながら根拠を集めて `submit_answer` で確定する。

| 道具 | 役割 |
|---|---|
| `list_files` | 案件やパターンでファイルを絞り込む |
| `search_corpus` | 抽出済み全文へのキーワード検索 |
| `read_document` | 本文を読む。offset で続き、grep で範囲を絞る |
| `locate_in_pages` | 語がどのページにあるかを引く |
| `lookup_glossary` | 略称と案件名の対応を用語集から引く（259語） |
| `run_python` | サンドボックスで集計・相関・閾値探索を実際に計算する |
| `list_images` | ファイルや案件に紐づく画像を列挙（639件） |
| `view_image` | 図・座席表・画像PDF を実際に見る |
| `submit_answer` | 回答・根拠・確信度を提出する |

1問あたりの道具呼び出しは中央値 8 回、平均 11.7 回、最大 84 回。100問で計 1,171 回。

### 安易な「わかりません」を突き返す

配点設計は正しく怖がらせる一方で、**少し探せば分かることまで諦める**副作用を生む。そこで、道具の呼び出しが 9 回に満たないうちに諦めの語を含む回答を出そうとしたら、一度だけ差し戻して具体的な追加手段を提示する仕組みを入れた。

1. `read_document` の offset を進めて最後まで読む
2. grep に別の語（言い換え・英語表記・略称・列名）を指定する
3. 複数案件にまたがる集計なら `run_python` で全案件を一括走査する
4. 図やスキャンPDFなら `list_images` → `view_image` で該当ページを見る

同時に、差し戻しの文面には**「推測を求めているのではない」と明記**した。探索を促す圧力はそのままにすると当てずっぽうを誘発する。問われている対象を取り違えたまま計算する誤りや、近そうな別の指標で代用する誤りは、いずれも「確認できない」より低い評価になるためである。

## 7. DGX Spark で戦うための工夫

本システムの技術的な中心はここにある。**フロンティアモデルを使えば不要だった作業**が、ローカル完結を選んだことで必要になった。

### 7.1 機材の性質を理解する

DGX Spark（GB10）は 128GB の統合メモリを持つが、メモリ帯域は約 273 GB/s しかない。コンシューマGPU（RTX 3090 で約 936 GB/s）に大きく劣る。

LLM の生成は**1トークンごとに全重みを読み出す**ため、帯域がそのまま速度を決める。

```
273 GB/s ÷ 18 GB（モデルサイズ）≒ 15 トークン/秒
```

**容量は潤沢だが帯域が細い**という非対称な機材であり、ここを前提に全ての設計判断を行った。

### 7.2 モデル選定 — 4モデルを実機評価

| モデル | サイズ | 判断 |
|---|---:|---|
| `gpt-oss:120b` | 65.4GB | **不採用**。ツール呼び出しのJSONが高頻度で破損 |
| `qwen3.8:27b-q8_0` | 30.0GB | 保留。q4との比較を公式採点で測れず |
| `qwen3.5:35b` | 23.9GB | 検証パス用に使用 |
| `qwen3.8:27b` | 17.7GB | **採用**（Q4_K_M / 文脈64k） |

`gpt-oss:120b` は MoE で帯域律速の機材と相性が良く、本命候補だった。しかし実行すると Ollama が 500 を返し、ツール呼び出しの引数JSONが壊れていた。

```
{"ext":"docx","project":"SOHK","query":"工数",top_k":20}      引用符の欠落
{"limit":200,"offset":500","plain":JSON?                       裸の値・途中で切断
{"code":"old = '''"+ (await None) + "'''"}                     JSON文字列内でPython連結
{"grep":"yellow", ... "株式会社青潮モビビ..."}                  文字の重複
```

**本番投入前にこれを検出できたことは収穫だった**が、JSONスキーマ制約付きデコードや修復リトライで押し切る時間がなく、断念した。この判断自体は後に見直すべきものとして記録に残している。

### 7.3 文脈長との戦い

当初は文脈 32k で運用していたが、**旧版と新版を突き合わせる差分比較の設問11問が、文脈溢れで一斉に壊れた**。

64k へ拡張したうえで、予算ベースの刈り込みを実装した。

```
CONTEXT_CHAR_BUDGET = 60000   予算を超えたら刈り込む
KEEP_FULL_RESULTS   = 4       直近4件の道具結果は原文のまま
MAX_TOOL_RESULT     = 14000   単一の結果の上限
```

予算超過時は、古い道具の結果から順に要約状態へ切り詰める。直近のものを原文で残すのは、エージェントが今まさに参照している情報を壊さないためである。

さらに、**差分比較は全文を読ませず `run_python` の `difflib` に寄せる**ようプロンプトで誘導した。変更行だけを見れば確実かつ短く把握できる。帯域が細い機材では、読ませる量を減らすこと自体が速度になる。

### 7.4 タイムアウト設計 — 1問ではなく1呼び出し

実行中、3問（Q14・Q40・Q85）が毎回 `model server unresponsive` で失敗した。当初はモデルの無応答を疑ったが、原因はクライアント側のタイムアウトだった。

**`RAG_TIMEOUT` は「1問」ではなく「1回のLLM呼び出し」の上限である。** これらはいずれも全案件を横断して集計する設問で、文脈が突出して大きくなり、1回のプリフィルが上限を超えていた。

```
420秒   Q14/Q40/Q85 いずれも失敗
900秒   Q14 回復（657秒・17呼）
1800秒  Q40 回復（v2と同一内容に到達）
```

**上限を上げるだけで2問が回復した。** 帯域律速の機材では、巨大な文脈の処理に一般的な設定値を大きく超える時間が要る。

### 7.5 障害への耐性

長時間実行を前提とするため、失敗が致命傷にならない設計を積み上げた。

**空応答をキャッシュしない** — LLM応答をキャッシュしていたが、空応答まで保存すると一度の失敗が永続化する。空は決して保存しない。

**500エラーの即時修復** — Ollama が `no user query found in messages` で 500 を返す場合がある。再試行を待つと1回あたり60秒を浪費するため、ユーザーターンを補って即座に再送する。

**無応答サーバの早期検知** — 84分間ハングしたまま検知できなかった事故を受け、応答の有無を監視して早期に打ち切る。

**提出物の安全ゲート** — エラーが全体の20%を超える場合、提出ファイルを上書きしない。`time` の import 漏れで100問が一斉にエラーになり、その「成功した実行」が提出物を破壊した事故への対策である。

**検証実行は提出物に触れない** — 検証用の実行が `submit/` を30行で上書きし、スコア 0.05 を記録した事故があった。以降、`test` 以外の実行は別ディレクトリに書き出す。

### 7.6 並列度の発見

1並列で100問6時間という前提のまま進めていたが、終盤に並列実行を試した。

```
同一設問 Q2   1並列(27b)  27.0秒
             3並列(35b)  31.4秒   ← 遅延は16%増のみ
```

接続数を確認して実際に3本が同時実行されていることを検証した。**遅延が16%しか増えないということは、総スループットが約2.6倍**になっている。

帯域律速の機材では、複数リクエストが重みの読み出しを共有するため、バッチ処理が効く。**これを早く測っていれば1実行2.5時間となり、12時間の再現枠に3回の実行が収まって、断念した多数決が実現できた。**

### 7.7 運用

- ネットワーク越し（`192.168.10.116`）での遠隔実行。Ollama の待ち受けアドレス設定から構築
- 進捗ログを実行器に内蔵し、1問完了ごとに経過・呼び出し回数・回答冒頭を追記
- 全力稼働で 90°C 級の発熱に達するため、無人環境での長時間実行には注意を要する

## 8. 評価基盤 — 自己採点の失敗と是正

初期は回答したモデル自身に採点させていた。結果は **0.9000**。

主催者の採点器（`crag.py`、判定モデルは gpt-5.2）で同じ回答を採点すると **0.7333** だった。**自分の冗長さを甘く採点していた**ことになる。

ここで評価基盤を作り直した。

- 正解データのある検証セット30問に対して公式採点器を回す仕組みを整備
- 改善の採否はこのスコアでのみ判断する
- APIキーは採点にのみ使用し、回答生成はローカルに限定する

この是正によって初めて、施策の良し悪しを客観的に判定できるようになった。

## 9. 結果

テスト100問は Public 30問・Private 70問に分割されていた。スコアを整数に戻すと分母が判明する。

| 提出 | Public (30問) | 素点 | Private (70問) | 素点 |
|---|---:|---:|---:|---:|
| **v2（最終選択）** | **0.7333** | 22.0 | **0.5071** | 35.5 |
| v4（プロンプト調整版） | 0.6333 | 19.0 | 0.5000 | 35.0 |
| 不完全な提出（30行） | 0.2333 | 7.0 | 0.2357 | 16.5 |
| 破損した提出 | 0.0500 | 1.5 | 0.2786 | 19.5 |

### 失点の構造

Private のスコアから内訳を逆算すると、概ね次のようになる。

```
Perfect  約50問
Incorrect 約14問   ← 1問あたり2点の損失
Missing   約6問
```

**誤答14問を潰すだけで 35.5 → 63.5（0.907）に届く。** 答えられないことではなく、間違って答えていることが問題だった。

### 誤答の性質

取りこぼした設問を精査すると、ほとんどが**正しい案件の中で間違えた**ものだった。

| 設問 | 内容 | 誤りの性質 |
|---|---|---|
| Q10 / Q29 | ヒストグラムの度数・ビン範囲 | 画像を目視で読んだ |
| Q44 / Q58 | 座席表の位置関係・内線番号 | 同上 |
| Q57 | 閾値を変えたときのF1最大値 | 計算させずに答えた |
| Q7 | ピボットの抽出条件 | 正しい案件内での取り違え |
| Q1 | old版との差分 | 正しい案件内での見落とし |

**いずれも決定的な計算で答えが一意に決まる設問である。** これらをモデルに「見せて読ませて」いたことが、失点の主因だった。

---

## 10. 試して効かなかった施策

測定した上で採用を見送ったものを記録しておく。

### 回答の検証パス

誤答を Incorrect(−1) から Missing(0) に変えれば 1問あたり +1 点になる。そこで、回答後に**まっさらな状態の別エージェントが独立に資料を確認し、否定されたら棄権する**パスを実装した。

| 構成 | 測定結果 | 判定 |
|---|---|---|
| 同一モデルで検証 | 検証30問で誤答1件を捕捉（+0.0333）。しかし本番36問連続で否定ゼロ | 実質無効 |
| 別モデル（35B）で検証 | 唯一の否定が**正答に対する誤否定**（−0.0333） | 逆効果 |

機能しなかった理由は明確である。**検証役が回答役と同程度に弱い。** 同一モデルは自分の答えを支持し、別モデルは自信を持って正答を否定した。誤りを見抜くには、誤りを犯さない側の能力が要る。ローカルモデル同士では、この非対称性を作れなかった。

### 1問あたりの時間上限

長引く設問を打ち切って効率化しようとしたが、調べると**長時間設問24問のうち18問は「働いていたから長かった」**。850秒・49回の呼び出しを経て正答に到達した設問もあった。導入を撤回した。

### 回答の簡潔化

冗長さが減点要因という仮説を立てたが、実測すると回答は既に**平均17文字・中央値7文字**で、150文字超は0件だった。伸びしろ自体が存在しなかった。

### 多数決（self-consistency）

同じ設問を3回解いて一致を採る手法は有効と判断したが、1実行6時間 × 3 = 18時間となり、再現12時間の制約に収まらず断念した。**7.6 の並列度を先に測っていれば実現できていた。**

## 11. 振り返り

### リーダーボードを改善の物差しにしていた

最大の失敗はこれである。

v2 と v4 の差は、**Public で 3点（0.1000）、Private で 0.5点（0.0071）**だった。Public は30問しかなく、3問ぶれれば 0.1 動く。この差を「プロンプト変更の効果」と解釈し、方針決定の根拠にしていた。Private の結果は、それが効果ではなく**揺らぎ**だったことを示している。

手元には正解データ付きの検証セットと公式採点器があった。測定の分解能を超えた意味を読み取らない規律が、技術的な工夫より先に必要だった。

### 機械で解ける設問を機械で解くべきだった

失点の中心は、ヒストグラムの度数、座席表の位置関係、閾値探索、ピボットの抽出条件だった。いずれも決定的な計算で答えが一意に決まる。生データからExcelの分割規則で再計算する、画像の座標関係を解析する、といった実装に向かうべきだった。

**これはモデルの強さとは独立した改善であり、ローカルLLMのままでも実行できた。** フロンティアモデルとの差を埋める現実的な道は、まずここにあった。

### 機材の特性を測るのが遅かった

並列度の効果（2.6倍）を最終日まで測っていなかった。帯域律速の機材ではバッチ処理が効くという性質は事前に予測できたはずで、**最初に10分かけて測るべき種類のこと**だった。

### ローカル完結という選択について

この方針は精度を犠牲にした。一方で、得られたものもある。

- **外部APIへデータを一切送出しないシステムが実際に動いた** — 社内ドライブという題材において、これは機能要件に相当する
- **コスト構造が実行回数から独立した** — 6時間の実行を何度でも回せた
- **ハードウェアの制約が設計を規定する経験を得た** — 文脈長、タイムアウト、並列度、量子化、どれも帯域と容量から逆算する必要があった

結果として 0.5071 に留まったが、**その差がどこから来たかを数値で特定できている**。誤答14問のうち、モデルの能力に起因するものと、実装で防げたものが分けられている。次に同じ制約で取り組むなら、まず後者から潰す。
