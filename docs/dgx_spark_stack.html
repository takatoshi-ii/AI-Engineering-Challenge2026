DSparkarXiv:2607.05147

Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation — 2026年7月6日投稿

一次情報で確認 著者は33名で、DeepSeek の Wenfeng Liang を含みます。論文自体が DeepSeek-V4 のサーバシステム上で実トラフィックを使って評価されており、研究成果というより本番投入された仕組みの報告という性格です。

解こうとしている問題

投機的デコードは「安いドラフトモデルに先読みさせ、本命モデルが並列に検証する」手法です。近年の並列ドラフタは1回の順伝播で長いトークン列を提案できますが、二つの弱点があります。

  • 受理率の急速な減衰 — トークン間の依存関係を持たないため、ブロックの後ろへ行くほど当たらなくなる（suffix decay）
  • バッチ容量の浪費 — 棄却される可能性の高いトークンまで一律に検証するため、多重同時実行時にスループットが落ちる

二つの仕掛け

半自己回帰アーキテクチャ。 計算量の大きいドラフト用バックボーンは完全並列のまま保ち、そこに軽量な逐次出力ヘッドだけを付け足すことで、局所的な遷移情報を注入します。並列モデルのドラフト速度を保ったまま suffix decay を緩和する、という設計です。

信頼度スケジュール検証。 位置ごとの「接頭辞が生き残る確率」を推定する信頼度ヘッドと、ハードウェア特性を織り込んだスケジューラを組み合わせ、リクエストごとに検証長を動的に決めます。GPU に余裕があれば深く投機し、混んでいれば浅くする、という負荷対応です。

DFlasharXiv:2602.06036 / ICML 2026

Block Diffusion for Flash Speculative Decoding — v1 2026年2月5日、v2 2026年5月28日

一次情報で確認 著者は Jian Chen、Yesheng Liang、Zhijian Liu の3名（Z Lab）。ICML 2026 採択。DSpark より半年早く、系譜としては先行します。

拡散モデルをドラフタに使う

従来手法（EAGLE-3 など）のドラフト生成は自己回帰的で、1トークンずつ順に出すため逐次処理から逃れられません。DFlash はここを置き換えます。

軽量なブロック拡散モデルが、1回の順伝播で K トークンのブロック全体を並列に生成します。ドラフトモデルは本命モデルから抽出した文脈特徴を条件として受け取り、本命モデルは K トークンを並列に検証します。

なぜ効くか

並列であるため、ドラフト予算（K）を増やしてもレイテンシがそれに比例して増えません。従来の投機的デコードが頭打ちになっていた「先読みを深くすると遅くなる」という制約を外せる、というのが主張の核です。

報告値内容確認
6倍超ロスレス加速（複数モデル・複数タスク）確認
最大 2.5倍EAGLE-3（当時のSOTA）に対する上乗せ確認

「ロスレス」は重要な語です。投機的デコードは検証を本命モデルが行うため、出力分布が変わりません。量子化や蒸留と違い、速度と引き換えに精度を失わないという性質があります。

確認できなかった点

ドラフトモデルの規模、学習方法、評価に使ったハードウェアは、abstract ページからは取得できませんでした。実装検討の際は PDF 本文の確認が必要です。

NVIDIA 公式ナレッジベースa_id 5780 / 移植ガイド

DGX Spark で「できないこと」の公式見解 — GPUDirect RDMA 非対応

一次情報で確認 ナレッジベース記事本体（a_id/5780）は自動取得が 403 で拒否されるため、同内容を記載した公式移植ガイドと開発者フォーラムで確認しました。

動かないもの

GPUDirect RDMA        非対応
  ├─ nvidia-peermem   動作しない
  ├─ dma-buf          動作しない
  └─ GDRCopy          動作しない

理由は統合メモリそのもの

公式の説明はこうです。ピン留めデバイスメモリ確保子（cudaMalloc など）が返すシステムメモリは、CPU コンプレックスからも、PCI Express 上の I/O 周辺機器（Mellanox NIC など）からもコヒーレントにアクセスできない。

本調査での解釈 より根本的には、GB10 には GPU 専用メモリが存在しません。あるのは CPU に接続された LPDDR5 だけです。NIC が直接データを書き込むべき「GPU のメモリ」が物理的に無いため、GPUDirect RDMA という概念自体が成立しません。

回避策（公式）

アプリケーションは実行時に CU_DEVICE_ATTRIBUTE_GPU_DIRECT_RDMA_SUPPORTED と CU_DEVICE_ATTRIBUTE_DMA_BUF_SUPPORT を問い合わせ、対応可否を自分で判定すること。Linux の RDMA アプリケーションでは、通信バッファを cudaHostAlloc で確保し、ib_reg_mr で登録する。

本調査での解釈 これは複数台クラスタを組む際に直接効いてくる制約です。NVIDIA 自身が2〜4台構成を公式にサポートしている一方で、ノード間のデータ移動は GPU 直結の RDMA ではなく、ホストメモリを経由する経路になります。単体運用では意識する必要はありませんが、スケールアウトを前提に設計するなら最初に把握しておくべき点です。

DGX Spark 1台で 84.7 GiB のモデルを 0.94M コンテキストで動かした実測記録

記事のみ・未確認 以下は Pju 氏による実機検証の記述です。一次情報（llama.cpp のソース）での裏取りは行っていませんが、コミットハッシュ・具体的な数値・失敗の記録まで含む詳細な手順書であり、他のどの資料よりも実運用に近い情報です。

Qiita 記事の表題は 115 tok/s、本記事の実測はエージェント運用で 20.3 t/s、決定論的出力でも 50〜54 t/s です。条件（台数、バッチ、セッション集約、出力の性質）が異なるため単純比較はできませんが、カタログ的な最大値と実運用の値には数倍の開きがあると考えるべきです。私たちの用途はエージェント推論なので、参照すべきは 20 t/s 台の方です。

品質と運用の注意

  • 2bit量子化の限界 — UD-IQ2_M は思考OFF時に算数を誤る（2+2=5 が温度0で再現）。思考ONなら正答。量子化を攻めるなら思考モードとの併用が前提
  • 起動に約6分 — モデルロード。常駐運用が前提になる
  • 並列不可 — --parallel 1 固定のためリクエストはキューイングされる
  • 巨大な cold リクエスト — 198K トークンの prefill で約18.7分（177 t/s）
  • 停止コマンド — pkill -x llama-server。pkill -f は SSH セッション自体を巻き込んで落とす

発熱への対処

著者は gb10-thermal-governor（MITライセンス）を自作し、GPU クロックを PID 制御しています。DGX Spark は全力稼働で 90°C を超えるため、設定温度 80°C を保ちながらスループットを最大化する仕組みです。実測でクロックを 2007〜2881 MHz に絞りつつ、温度誤差 ±4°C、パニック閾値 94°C には未到達とのこと。無人環境での長時間運用には、この種の制御が要ります。

この機材にとっての意味

帯域律速という弱点に、投機的デコードがなぜ効くのか

本調査での解釈 DGX Spark の帯域は約273 GB/s で、コンシューマGPU（3090で約936 GB/s、5090で約1,800 GB/s）に大きく劣ります。密モデルの生成では、毎トークン全重みを読むため、この差がそのまま速度差になります。

投機的デコードがこの機材と噛み合う理由は、ボトルネックの付け替えにあります。

通常のデコード   1トークンごとに全重みを読む   → 帯域を使い切る／演算は遊ぶ
投機的デコード   Kトークンをまとめて1回で検証   → 演算を使う／帯域の読み出し回数が減る

本命モデルの重み読み出しが K 分の1に減り、代わりに余っていた演算資源が使われます。余っている資源で、詰まっている資源を肩代わりする構図であり、演算に余裕があって帯域が細い機械ほど利得が大きくなります。DGX Spark はまさにその形をしています。

実測との照合

私たちが Ollama で密27B（Q4_K_M / 18GB）を回したときの実効はおよそ14 tok/sでした。同じ機材での他者の実測は次のとおりです。

桁違いに大きいモデルが、密27Bより速い。 MoE のスパース性、低ビット量子化、投機的デコード、カーネル最適化の積み上げによるものです。一方で、エージェント推論という私たちの用途では 20 t/s 台に落ち着く点も押さえておく必要があります。

取るべき順序

  • 密モデルをやめて MoE へ。 これが最も効きます。活性10〜15B の 100〜130B MoE が vLLM 公式の推奨帯です
  • 推論基盤を Ollama から乗り換える。 vLLM（公式の推奨構成と実測値が揃う）か llama.cpp（DSpark 対応済み・巨大文脈が可能）。ツール呼び出しのパース経路が異なるため、gpt-oss:120b で遭遇した JSON 破損が解消される可能性があり、これは保留中の課題への回答にもなります
  • 投機的デコードは条件を選んで使う。 MTP は既に vLLM の CUDA Graph に載り、DSpark は llama.cpp に実装済み。ただし受理率は出力の決まりやすさ次第で、自由な日本語生成では利得が半減します
  • 発熱制御を先に用意する。 全力稼働で90°Cを超えます。長時間の無人実行を行うなら、クロック制御なしには回せません
