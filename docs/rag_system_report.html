前提

設問を知らないシステムを作る

このコンペの核心は精度ではなく制約にあった。禁止事項が、設計の自由度をほぼ決めてしまう。

規約は、人手で整理した一覧表の読み込み、設問ごとの参照ファイルや正解候補の事前作成、質問文を見て固定回答を返す分岐、特定案件名やファイル名を狙い撃ちした処理を、いずれも禁じていた。答えの金額・担当者名・ページ番号・セル番地をコードやプロンプトに書くことも認められない。

この制約を素直に受け取ると、作れるものは一つに絞られる。形式ごとの汎用的な読み取り器と、それを道具として使うエージェントである。案件の略称も、保護ファイルのパスワード導出規則も、決裁基準も、すべて実行時にドライブ内の該当文書を読んで解決させる。未知の案件フォルダが増えても同じ処理で動くことが、規約適合の証明そのものになる。

設計上の帰結

質問文による分岐は一箇所も存在しない。100問すべてが同一のエージェントループを通る。案件はフォルダ走査で列挙し、用語集に無い案件はフォルダ名で登録するフォールバックを持つ。

4段のパイプライン

抽出

書式そのものが答えになる

「太字の箇所は」「黄色ハイライトのセルの条件は」「何ページ目に載っているか」。この種の設問は、本文テキストだけ抜き出しても永久に解けない。

そこで抽出テキストに書式を埋め込む方式を採った。[[bold]]…[[/]]、[[hl:yellow]]…[[/]]、[[color:red]]…[[/]] のようなマーカーを本文中に差し込むことで、書式に関する問いが通常のテキスト検索の問いに変わる。図形の塗りは「塗り=red(...)」として書き出す。

技法 Aテーマ色と tint の解決

OOXML はセルや文字の色を「テーマ色の番号＋明度補正(tint)」で持つことがある。番号のままでは黄色かどうか判定できないため、theme1.xml を読んで実際のRGBに解決する。少数派の色をハイライトとみなすヒューリスティクスと組み合わせて、初めて「黄色ハイライト」が扱える。

技法 Bヒストグラムは chartEx にいる

Excel 2016以降のヒストグラムは通常のグラフXMLではなく chartEx パートに、ビン分割の定義とともに格納される。ここを読まないとビン幅も度数も取れない。ただし今回のデータでは、ヒストグラムが画像として貼られているブックもあり、そちらは最後まで正しく解けなかった。

技法 Cページ番号はXMLに存在しない

docx や pptx に「何ページ目か」という情報は無い。レンダリング結果として初めて決まる。そこで MS Office の COM オートメーションで実際に開かせ、レイアウト実測のページ割りを取得して抽出テキストに書き込んだ。

技法 D斜体が斜体でない

あるPDFのイタリックはフォント属性ではなく、テキスト行列 Tm の傾き成分（c≈0.3333）で擬似的に作られていた。フォントフラグを見るだけでは検出できないため、コンテンツストリームを解析して行列の歪みから斜体を判定している。

技法 Eパスワードは規則から導く

保護されたファイルのパスワードは、ドライブ内の規則文書に書かれたテンプレートから実行時に導出する。パスワードそのものをコードに書けば規約違反になるため、規則を読んで組み立てる以外に道がない。

検索

形態素解析を使わない理由

日本語の索引付けに文字バイグラム（＋ASCII語をまとめて1トークン）を選んだ。辞書が要らず、決定的で、employment_length や Attr14 のような識別子めいた語を分割せずそのまま一致させられる。形態素解析器は未知語の切り方が辞書に依存し、この種の語彙を壊しやすい。

BM25    k1 = 1.4    b = 0.72
チャンク  5,877 件      語彙  72,998 種

埋め込みベクトルによる意味検索は使っていない。設問の多くが「この案件のこのファイルの、この列」という指示的なもので、語の一致が効く。加えて、外部埋め込みモデルへの依存を避けられる利点があった。

推論

エージェントは最大26手のループを回り、道具を呼びながら根拠を集めて submit_answer で確定する。

工夫 1文脈の刈り込み

会話は呼び出しのたびに膨らむ。60,000文字の予算を超えたら、直近4件の道具の結果は原文のまま、それ以前は要約状態に切り詰める。単一の結果は14,000文字で頭打ちにする。旧版と新版の全文を両方読ませると文脈が溢れて回答不能になるため、差分比較は run_python の difflib に寄せるようプロンプトで誘導した。

工夫 2安易な「わかりません」を突き返す

採点は誤答が −1点、「わからない」が 0点。この設計は正しく怖がらせる一方で、少し探せば分かることまで諦める副作用を生む。そこで、ツール呼び出しが9回に満たないうちに諦めの語を含む回答を出そうとしたら、一度だけ差し戻して具体的な追加手段を提示する。offsetを進める、語を言い換える、全案件を一括走査する、画像を見る、の4つである。

やってはいけない誘導

差し戻しの文面には「推測を求めているのではない」と明記した。探索を促す圧力は、そのままにすると当てずっぽうを誘発する。問われている対象を取り違えたまま計算する誤り、近そうな別の指標で代用する誤りは、いずれも「確認できない」より低い評価になる。

工夫 3画像を検索可能にする

OCRの結果を索引に載せていなかった当初、画像内の情報は view_image で直接見に行かない限り到達できなかった。253枚の読み取り結果をチャンクとして索引に加えたことで、キーワード検索から画像内の記述に届くようになった。

評価

自分で自分を採点してはいけない

初期は回答したモデル自身に採点させていた。結果は 0.9000。同じモデルを公式採点器にかけたときの実測は 0.7333 で、自分の冗長さを甘く採点していた。

主催者の crag.py（判定モデルは gpt-5.2）をそのまま回す仕組みに切り替えてから、初めて改善の判定が可能になった。正解データのある検証セット30問に対して公式採点を回し、そこでのみ良し悪しを決める。回答生成にはローカルモデルだけを使い、APIキーは採点にしか使っていない。

Perfect     +1     完全正解
Acceptable  +0.5   軽微な誤りを含む有用な回答
Missing      0     わからない
Incorrect   −1     誤答・無関係

この配点の含意は大きい。誤答は1問につき2点の損失になる。取れるはずの +1 を落とし、さらに −1 を負うからである。

30問で判断してはいけなかった

Public は30問しかない。3問ぶれれば 0.1 動く。私はこの差を「プロンプト変更の効果」と解釈し、方針決定の根拠にしていた。Private の結果は、それが効果ではなく揺らぎだったことを示している。

取りこぼしの内訳を逆算すると、Perfect 約50問・Incorrect 約14問・Missing 約6問となる。誤答14問を潰すだけで 35.5 → 63.5、すなわち 0.907 に届く。答えられないことではなく、間違って答えていることが問題だった。

学び

次に同じ課題をやるなら

01機械で解ける設問を機械で解く

失点の多くは、ヒストグラムの度数、座席表の位置関係、閾値を動かしたときのF1最大値、ピボットの抽出条件だった。いずれも決定的な計算で答えが一意に決まる。これらをモデルに「見せて読ませて」いたことが誤答の主因である。ヒストグラムを画像として読ませるのではなく、生データからExcelの分割規則で再計算する。座席表は画像の座標関係を解析する。モデルを賢くするより確実で、しかも安い。

02並列度を最初に測る

1並列で100問6時間という前提のまま最終日まで進めた。終盤に3並列を試すと、同一設問の所要時間はわずか16%増で、総スループットは約2.6倍だった。DGX Spark は帯域律速で、バッチ処理が効く。これに早く気づいていれば1実行2.5時間となり、12時間枠に3回の実行が収まって多数決が実現できた。

03MoE を諦めない

120B級のMoEは活性パラメータが約5Bで、密27Bより3倍前後速い可能性が高い。帯域律速の機材ではむしろMoEが有利になる。今回はツール呼び出しのJSONが23%の確率で壊れて断念したが、これは推論能力ではなく出力形式の問題であり、スキーマ制約デコードか修復リトライで潰せたはずだった。

04リーダーボードを改善の物差しにしない

Public 30問の変動に方針を合わせ続けたことが、一貫した失敗だった。手元には正解データ付きの検証セットと公式採点器があった。測定の分解能を超えた意味を読み取らないという規律が、技術的な工夫より先に必要だった。
